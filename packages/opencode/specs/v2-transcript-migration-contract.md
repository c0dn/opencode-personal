# V2 Transcript Migration Contract

## Purpose

This contract closes the planning requirements for v2 transcript migration before mapper or backfill implementation begins. Broad transcript backfill is not present in the current runtime slice and remains out of scope here. The current implemented remediation is limited to the narrow task-tool metadata marker documented below. Any future broad migration must be lazy/on-read and per session: when a session is read through the v2 path, legacy transcript rows are mapped directly into `SessionMessageTable` with insert/upsert semantics. The migration must not synthesize `EventV2` history. Legacy `msg_` and `prt_` identifiers are migration-only implementation inputs and must not become canonical v2/API-visible identifiers.

The consumer migration target is a no-adapter v2 cutover. Old clients are assumed to move with server versions, so old-version clients never connect to newer servers. The migration therefore does not preserve legacy HTTP wire shape, legacy cursors, legacy `parts(messageID)` behavior, or synthetic legacy-compatible IDs. Transitional tests may use legacy readers as an oracle while both implementations exist, but post-cutover behavior must use canonical v2 IDs, v2 cursors, v2 payloads, and observable v2 gates/errors rather than legacy fallback.

- `packages/core/src/session/legacy.ts` defines legacy message `Info`, part `Part`, and hydrated `WithParts`. The part union is `text`, `subtask`, `reasoning`, `file`, `tool`, `step-start`, `step-finish`, `snapshot`, `patch`, `agent`, `retry`, and `compaction`. Assistant errors are auth, unknown, output length, aborted, structured output, context overflow, and API.
- `packages/core/src/session/sql.ts` defines the legacy `MessageTable` and `PartTable`, the v2 `SessionMessageTable`, and the shared `SessionTable`.
- `packages/core/src/data-migration.sql.ts` and `packages/core/src/database/migration/20260511000411_data_migration_state.ts` define the `data_migration` marker table used to record completed data migrations. The current narrow task-tool metadata remediation marker is `legacy-session-message-backfill/v3/task-tool-metadata/<sessionID>`.
- `packages/core/src/session.ts` defines `SessionV2.messages` and `SessionV2.context` over `SessionMessageTable`, sorted by `time_created` and `id`; `context` anchors on the newest v2 compaction row.
- `packages/core/src/session/message.ts` defines the v2 `SessionMessage` schema: user, synthetic, shell, assistant, compaction, agent-switched, and model-switched messages, plus assistant text/reasoning/tool/patch content. Retry metadata lives on the assistant message, not in the `AssistantContent` union. User-side task requests now exist as `SessionMessage.User.taskRequests[]` entries using `UserTaskRequest`; assistant-owned legacy patches now exist as `AssistantPatch` content.
- `packages/opencode/src/session/message-v2.ts`, `packages/opencode/src/session/compaction.ts`, `packages/opencode/src/session/prompt.ts`, `packages/opencode/src/session/summary.ts`, and `packages/opencode/src/session/revert.ts` are current legacy transcript consumers for model context, compaction, prompt flow, summary/diff, and revert behavior.
- HTTP/API groups and handlers under `packages/opencode/src/server/routes/instance/httpapi` expose legacy and v2 session/message surfaces, pagination, and events while the cutover is in progress.
- `packages/opencode/src/cli/cmd/import.ts` and `packages/opencode/src/cli/cmd/export.ts` import/export legacy `SessionLegacy.Info` and `SessionLegacy.Part` shapes and must remain compatible until those flows are migrated.

## Identity, Ordering, and Provenance

Backfilled v2 IDs must be deterministic and migration-owned. Row IDs use `evt_legacy_backfill_m_<fixedWidthBase36Ordinal>_<shortHash>`. Nested assistant content IDs use `evt_legacy_backfill_c_<fixedWidthBase36MessageOrdinal>_<fixedWidthBase36ContentOrdinal>_<shortHash>`. Message ordinals come from legacy messages sorted by `(MessageTable.time_created, MessageTable.id)`. Content ordinals come from parts for a message sorted by `PartTable.id`; content created from multiple parts uses that part order. A compaction summary pair uses the marker message ordinal plus a content ordinal derived from the paired summary parts. Ordinals are 8-character zero-padded base36 strings. If a message or content ordinal exceeds that width, the mapper fails loudly for that session instead of producing unstable IDs.

The short hash is SHA-256 over migration version, session ID, legacy message ID, optional part ID or ordered part IDs, target kind, and ordinal inputs. Encode the first 12 bytes as lowercase hex. Raw `msg_` or `prt_` strings may be hash inputs but must not appear in canonical/API-visible v2 IDs or metadata. A deterministic ID collision with an existing non-migration row fails and must not overwrite that row. A collision with a migration-owned row is repairable only when the existing row corresponds to the same deterministic source hash.

`time_created` copies the legacy message time for mapped messages and the relevant part time for content that becomes a standalone v2 row. V2 reads sort by `time_created,id`, matching `packages/core/src/session.ts`. For backfilled rows with the same timestamp, the deterministic ordinal and ID must produce stable and reasonable ordering: user turn, associated assistant, assistant content/progress-derived rows, then compaction where applicable. In v1 mixed sessions, backfilled rows are not interleaved before live rows at the same timestamp; an equal timestamp boundary is ambiguous and leaves the session unmarked.

Migration ownership for v1 backfilled rows is determined by the deterministic `evt_legacy_backfill_` ID prefix plus non-public in-memory/source mapping held during the transaction. Do not write raw source IDs, source hashes, or migration provenance into `SessionMessage.metadata`; that field is public. `SessionMessageTable` has no private provenance column in v1. Public HTTP/API payloads, SDK output, export payloads, and v2 display metadata must not expose raw legacy IDs. No v1 public metadata provenance is allowed.

## Durable Task Tool Metadata Prerequisite

Parent subagent task-tab discovery cannot move from legacy transcript reads to v2 display/bootstrap until task-tool child-session metadata is represented durably in canonical v2 rows. This is a narrow prerequisite for display/bootstrap state only; it is not a provider-visible model-context feature, a general metadata exposure mechanism, a v2-to-legacy adapter, or a synthetic legacy-ID policy.

### Canonical shape

Task tool metadata must live under the nested structured key:

```ts
AssistantTool.state.structured.task = {
  sessionID: string
  toolCalls?: number
}
```

The `task` wrapper is required so task metadata cannot collide with ordinary tool result structured data. Updaters and projectors must merge this nested `task` object into running, completed, and error task tool `state.structured` values without overwriting unrelated structured result fields. If a completed/error tool already has other structured output, the merge preserves those fields and replaces only `structured.task` with the sanitized task metadata.

### Durable event

Use a new durable/sync EventV2 event for task metadata updates. Do not reuse `Tool.Called`, because child-session metadata can become available or be repaired independently of the call-start event and must be replayable without broadening call input metadata.

Suggested event name: `session.next.tool.metadata.updated`.

Required event data:

- `sessionID`: parent session that owns the assistant/tool row.
- `assistantMessageID?`: canonical v2 assistant message ID when known; optional only for compatibility with live windows that can still target by call ID.
- `callID`: tool call ID for the task tool to update.
- `task`: unwrapped sanitized task metadata `{ sessionID, toolCalls? }`.
- `timestamp`: numeric timestamp used for durable replay/sync ordering.

The event is narrow to safe task-tool metadata used for canonical display/bootstrap. It must not be included in provider-visible model context, must not expose arbitrary `ctx.metadata()` values, and must not carry raw legacy message/part IDs, private provenance, job IDs, parent-session IDs, background flags, model names, or unreviewed tool metadata. The updater/projector writes the event data as `state.structured = { ...state.structured, task: event.data.task }`; it must not produce `structured.task.task`.

Live publishers must include `assistantMessageID` whenever it is known. Missing-target fallback is allowed only for one active/incomplete matching task tool in the current assistant. Completed or error task tools must not be updated without an explicit assistant target if more than one matching `callID` could exist. Metadata events for missing, non-task, or ambiguous tools are no-ops or typed failures according to the projector/updater contract; they must not update a different tool by `callID` alone.

### Shared sanitizer

There must be one sanitizer used by all three producers/remediation paths:

1. live `ctx.metadata()` projection before publishing/updating v2 task metadata,
2. `TaskTool` completion / `Tool.Success.structured` handling, and
3. legacy backfill/remediation when existing task tool rows are repaired.

The sanitizer whitelist is intentionally small:

- Accept `sessionID` from legacy/live `sessionId` or `sessionID`, canonicalize it to output key `sessionID`, and keep it only when it is a valid canonical session identifier for display/bootstrap.
- Accept `toolCalls` from `toolcalls`, `toolCalls`, or `calls`; keep it only when it is a finite non-negative number. Normalize the output key to `toolCalls`.
- Drop `toolCalls` when missing or invalid; drop the entire `task` object when no valid `sessionID` remains.
- Exclude `model`, `parentSessionId`, `jobId`, `background`, arbitrary metadata keys, provider/private metadata, raw `msg_*`/`prt_*` legacy IDs, and any unrecognized nested values from public/canonical structured output.

### Backfill, markers, and remediation

This slice implements only the narrow task-tool metadata remediation marker `legacy-session-message-backfill/v3/task-tool-metadata/<sessionID>`. It does not add broad transcript backfill, EventV2 synthesis, deletion/rebuild, or a v2-to-legacy adapter. A session marked only by an older backfill version may contain task tools lacking `structured.task`; the task-metadata remediation path must still run, detect eligible canonical task rows, and update them in place when the legacy source metadata can be sanitized. Older marker fast paths must not skip this prerequisite.

Legacy task metadata source policy is precise: only legacy `part.data.tool === "task"` rows are eligible, and only running/completed/error task states are considered. Candidate metadata comes only from `part.data.state.metadata` and may also accept an existing nested `part.data.state.metadata.structured.task` only if it satisfies the canonical sanitizer. Do not use top-level `part.data.metadata` for this remediation. The remediator must never copy the full legacy metadata object into v2 structured output.

If the legacy source rows are gone, remediation must not blindly delete or rebuild migration-owned rows. Preserve existing rows, report remediation stats for missing source or missing safe task metadata, and leave parent task-tab v2 discovery blocked for that session until a safe canonical source exists.

Parent task-tab discovery v2 cutover remains a later slice. This prerequisite is complete only after the durable event, updater/projector merge policy, shared sanitizer, live/completion/backfill use sites, marker/remediation behavior, and schema generation requirements are implemented and validated. Because this adds a durable public EventV2 schema, OpenAPI/SDK event schema regeneration and SDK typecheck are mandatory for the implementation slice.

## Mixed Session Cutoff and Live Races

For sessions that already contain non-backfill v2 rows, compute the earliest non-backfill v2 row cutoff using the exact v2 row sort key `(time_created, id)` for read ordering, but do not use lexical ID ordering to decide old-vs-live at an equal timestamp in v1. Normal eligible backfill rows are only legacy candidates with `legacy_time_created < cutoff_time_created`. If any legacy candidate has `legacy_time_created == cutoff_time_created` and cannot be proven to correspond to an existing migration-owned row, the backfill must return `mixed_cutoff_ambiguous`, write no completion marker, and leave the session retryable. Implementations may choose to write no rows once ambiguity is detected; if older rows were written before detecting ambiguity, the transaction must roll back. Equal-boundary skip-with-marker is not allowed in v1.

The backfill must run in an immediate/write transaction (`BEGIN IMMEDIATE` or DB-layer equivalent) covering marker re-check, cutoff read, legacy read/map, row writes, and marker write. It must never overwrite non-backfill rows. Migration-owned rows may be repaired or upserted when the deterministic ID prefix and in-transaction source mapping prove the same deterministic source hash. If the transaction is busy, conflicts, or a live writer adds a non-backfill row and changes the cutoff during migration, abort without writing the marker and retry on the next read.

## Marker, Version, and Remediation

The data migration marker key is `legacy-session-message-backfill/v1/<sessionID>`. The marker is written last, after all rows for that session are written and test-observable stats are returned. The existing `data_migration` table records only `name` and `time_completed`; v1 backfill stats are not durable. `ensureLegacySessionMessagesBackfilled` must return per-session stats and log them for tests/operations during the backfill call only, but the marker records only completion. Skipped/degraded stats are not consumer-visible after the marker and are not carried in API, export, or SDK payloads. Consumer-visible degraded stats require a future private migration stats table and are outside v1.

Partial rows without a marker are retryable because deterministic IDs and the transaction's non-public source mapping allow repair/upsert. After the v1 marker exists, remediation can repair deterministic migration-owned rows by prefix and ID algorithm, but it cannot recover skipped/degraded stats from durable state. Recovering those stats requires rerunning with source rows under a new marker version.

The implemented v2 marker/remediation path uses marker names such as `legacy-session-message-backfill/v2/<sessionID>` and may transform migration-owned rows in place. Rebuild is allowed only when the legacy source rows still exist. If the legacy source is gone, do not delete backfilled rows blindly; preserve existing migration-owned rows and report remediation stats instead. Future mapper-output slices that newly represent legacy data must use this remediation path or define a newer marker version before changing backfill output.

## Compaction Contract

Only completed legacy compaction marker + paired summary assistant records map to `SessionMessage.Compaction`. The marker is a legacy user message containing a `compaction` part. The paired assistant must reference that user message, be marked as a summary, have no error, and have a completion/finish signal.

`reason` maps to `auto` when the legacy marker has `auto: true`; otherwise it maps to `manual`. `summary` is the joined text from the paired summary assistant, preserving paragraph order. `include` translates legacy `tail_start_id` to the deterministic v2 ID when that legacy ID was mapped and the mapping is safe. The `include` target must be a visible canonical row after tombstone/read filtering; tombstoned targets are omitted or rejected/not-ready, not treated as provable merely because the row is physically present. Omit `include` when the target cannot be proven. Incomplete pairs are skipped with stats and must not produce v2 compaction anchors.

For live EventV2 projection, `session.next.compaction.started` records only pending lifecycle state and must not create a canonical `SessionMessage.Compaction` row. `session.next.compaction.delta` is non-canonical; `session.next.compaction.ended` is authoritative and materializes exactly one completed row from the matching latest pending Started event: row ID and `time.created` come from Started, `reason` comes from Started, and `summary`/`include` come from Ended. Ended events without a matching pending Started are no-ops and must not create anchors.

Overflow-aware v2 compaction process selection is a pure canonical helper only. It consumes already-loaded canonical v2 rows, uses `(time.created, id)` ordering and existing v2 compaction/include visibility rules, and never reads DB/readiness, legacy transcript, plugin, provider prompt, or model-conversion state. Production wiring must either provide a canonical visible user `overflowReplayStartID` to replay from, or explicitly choose no replay/gate; the helper must not infer replay IDs from legacy `tail_start_id` or other non-canonical sources.

## Public Payload and Display Policy

This section began as the R6/U7a policy-only slice. It now records the U7 export-only checkpoint through U7e. The export-only sub-scope is complete, but the U7 parent remains open/in-progress because import, share, ACP/TUI/replay/display consumers, generated public schema work, and old legacy route/reader cleanup still have separate gates.

Completed U7 export-only commits:

- U7b `c3692e54f` — added display helper coverage needed by export fixtures.
- U7c `f51c0522f` — added public payload helper coverage.
- U7d `ef6858cc5` — added `export --format v2` export-only path.
- U7e `e457a056b` — omitted control rows from v2 export payloads.

These commits approve only the export CLI path for versioned v2 payload generation from already-gated canonical rows. They do not approve v2 import, share, generated schema/SDK/OpenAPI changes, ACP/TUI/replay migration, old legacy route deletion, destructive/session mutation behavior, or a v2-to-legacy adapter.

Two v2 outputs are required and intentionally separate:

- `PublicTranscriptPayloadV2` is the versioned, serializable, redacted payload for export/share/import-style public exchange. It uses canonical v2 IDs only, has an explicit `kind`/`version` envelope, and must not expose raw legacy IDs, private migration provenance, provider secrets, durable readiness diagnostics, or local-only display state.
- `DisplayTranscriptV2` is the ordered/renderable local display and replay shape for ACP/TUI/CLI/replay-style consumers. It uses canonical v2 IDs only and may include local display fields that are not appropriate for public payload exchange.

Later shared helper code may only centralize canonical ordering and exhaustiveness checks across these outputs. It must not define a v2-to-legacy adapter, legacy cursor emulation, old `parts(messageID)` behavior, or a single broad conversion shape that leaks public payload fields into display/replay or local display fields into public payloads.

### Payload envelope and import behavior

- V2 payloads require an explicit envelope such as `{ kind: "opencode.transcript", version: 2, ... }`. The exact field names may be refined by schema work, but the envelope must carry both kind and version and must be schema-tested before any public schema generation.
- V2 import accepts only the approved v2 envelope and `PublicTranscriptPayloadV2` schema. Unknown kinds, missing versions, unsupported versions, legacy payloads, and unwrapped arrays/objects are rejected by v2 import with a typed error.
- Existing legacy import may remain during transition for matching old payloads until the import cutover. That path is not a v2 import path and must not be used as best-effort v2 fallback.
- No best-effort legacy-to-v2 payload migration, old payload coercion, or legacy wire preservation is allowed unless a later explicitly approved slice defines the import policy and tests.
- Export-only `PublicTranscriptPayloadV2` is the first completed consumer after policy/helper tests. Import, share, ACP, TUI, and replay stay blocked until their own schema/fixture tests and readiness gates exist.

### Backfill/readiness gate

Payload/display helpers must accept only already-gated canonical rows plus explicit readiness metadata, or wrappers must hard-gate before calling them. Mixed, failed, partial, ambiguous, or missing-source states cannot be silently projected into public payloads or displays.

After cutover there is no legacy fallback: missing readiness returns the surface's typed not-ready/import/export/display error, retry instruction, or unsupported result according to that consumer's approved tests. Helpers must not read legacy transcript rows, infer legacy source state, or recover degraded stats from legacy tables.

## No-Adapter Semantic Test Plan

The test strategy is to prove behavior, not legacy wire equivalence. Fixtures should be source-neutral where possible: hand-author expected semantic outputs and, during transition only, compare normalized legacy helper output to canonical v2 helper output. Do not derive expected v2 fixtures by calling the mapper under test.

Fixture ownership:

- Core mapper/backfill fixtures stay in `packages/core/test/session/*` and must not import opencode test helpers.
- Opencode consumer fixtures may live under `packages/opencode/test/session/`, for example `transcript-semantic.fixture.ts`, and should cover model/context/API/consumer semantics.
- If both packages need the same cases, duplicate small fixture data or introduce an explicit package-local test-support module; do not make core tests depend on opencode test files.

Transitional tests:

- Legacy-oracle parity tests should be named as migration-only, for example `message-v2-legacy-parity.transitional.test.ts`.
- They may import `packages/opencode/src/session/message-v2.ts` only to prove pre-cutover semantic parity.
- Their retirement criterion is final removal or replacement when the last legacy consumer relying on that helper is deleted.
- Each new helper slice must state its own oracle retirement rule in the test file or adjacent plan note. Examples: R1 title oracle retires when title wiring reads only v2 or is intentionally skipped; R2 loop-control oracle retires when prompt no longer calls `MessageV2.latest/filterCompactedEffect`; R3 compaction oracle retires when residual compaction reads no longer call legacy session/message helpers; R4 doom-loop oracle retires when runtime detection no longer calls `MessageV2.parts`; R6/R7 oracles retire per consumer group when that group no longer uses old wire or legacy part IDs.

Permanent tests:

- `message-v2-model.test.ts` and `message-v2-context.test.ts` should assert expected v2 outputs directly.
- Core backfill tests remain as old-database migration regressions even after legacy writers/readers are removed.
